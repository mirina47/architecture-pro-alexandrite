# Выбор и настройка мониторинга в системе

## Мотивация
Текущие проблемы:
- Данные только из Яндекс.Метрики (покрывают лишь сайт онлайн-магазина).
- Потеря заказов и просрочки обнаруживаются только после жалоб. 
- MES тормозит из-за большой нагрузки.

Бизнес-ценность мониторинга:
- Предотвращение потери заказов в очередях и интеграциях.
- Раннее обнаружение инцидентов (до жалоб клиентов).
- Контроль SLA (время расчета стоимости, обработка заказов).
- Обоснованное масштабирование при росте нагрузки.
- Защита репутации и контрактов – гарантия выполнения обязательств перед партнерами.

## Выбор подхода к мониторингу
- Для API-сервисов (internet shop API, CRM API, MES API) — RED (Rate, Errors, Duration)
- Для инфраструктуры (серверы, базы данных, память, CPU) — USE (Utilization, Saturation, Errors)
- Для общей оценки — Четыре золотых сигнала (Latency, Traffic, Errors, Saturation)

## Метрики для отслеживания
**API (internet shop API, CRM API, MES API)**
| Метрика                                       | Зачем нужна                                                                | Ярлыки                                                |
|-----------------------------------------------|----------------------------------------------------------------------------|-------------------------------------------------------|
| Number of requests (RPS)                      | Контроль нагрузки, выявление пиков, планирование масштабирования           | service (shop/crm/mes), endpoint, method, status_code |
| Number of requests (RPS) per user             | Выявление аномалий, перегрузки со стороны отдельных клиентов или партнеров | service, user_id или partner_id, endpoint             |
| CPU %                                         | Определение насыщенности (saturation)                                      | service, instance_id                                  |
| Memory Utilisation                            | Выявление утечек памяти и приближения к лимитам	                         | service, instance_id                                  |
| Response time (latency)                       | Контроль SLA и выявление деградации                                        | service, endpoint, percentile (p50, p95, p99)         |
| Number of HTTP 200                            | Контроль успешных операций, расчет error rate                              | service, endpoint                                     |
| Number of HTTP 500                            | Обнаружение сбоев и ошибок обработки заказов                      	     | service, endpoint, exception_type                     |
| Number of simultanious sessions               | Контроль одновременной нагрузки и планирование масштабирования             | service, instance                                     |
| Kb tranferred (received)                      | Контроль сетевой нагрузки (актуально при передаче 3D-моделей)              | service, endpoint, status_code                        |
| Kb provided (sent)                            | Контроль сетевой нагрузки (актуально при передаче 3D-моделей)              | service, endpoint, status_code                        |

**RabbitMQ**
| Метрика                                            | Зачем нужна                                                                          | Ярлыки                  |
|----------------------------------------------------|--------------------------------------------------------------------------------------|-------------------------|
| Number of message in flight in RabbitMQ            | Контроль сообщений, которые находятся в обработке и еще не подтверждены consumer’ами | queue_name              |
| Number of dead-letter-exchange letters in RabbitMQ | Прямой индикатор ошибок обработки и потенциальной потери заказов                     | queue_name, routing_key |

**Базы данных**
| Метрика                                        | Зачем нужна                                                                      | Ярлыки            |
|------------------------------------------------|----------------------------------------------------------------------------------|-------------------|
| Memory Utilisation for shop/MES db instance    | Контроль насыщенности ресурсов БД и предотвращение деградации производительности | instance          |
| Number of connections for shop/MES db instance | Предотвращение исчерпания пула соединений и отказов при высокой нагрузке         | db_name, instance |
| Size of shop/MES db instance                   | Контроль роста данных, планирование масштабирования и бэкапов                    | db_name           |

 

## План действий
1. Определить ключевые метрики для API, инфраструктуры и бизнес-процессов.
2. Выделить первую партию сервисов для внедрения мониторинга.
3. Развернуть Prometheus + Grafana и подключить Alertmanager.
4. Интегрировать экспортеры метрик в API.
5. Настроить экспорт метрик RabbitMQ и баз данных.
6. Настройка дашбордов для мониторинга метрик.
7. Настроить алерты на пороговые значения.
8. Добавить при необходимости Jaeger для трассировки критичных процессов.


## Показатели насыщенности
| Метрика            | Пороговое значение        | Действие при превышении                            |
|--------------------|---------------------------|----------------------------------------------------|
| CPU %              | > 80% (в течение 5 минут) | Алерт, анализ, масштабирование                     |
| Memory Utilisation | > 85% лимита              | Алерт, проверка утечек, масштабирование            |
| DB connections     | > 85% лимита              | Алерт, проверка соединений, предотвращение отказов |
| RabbitMQ queue     |> 200 сообщений            | Алерт, проверка consumer’ов, уведомление команды   |
| HTTP 5xx           | > 1% трафика              | Алерт, создание тикета в Jira                      |

Действия при превышении порогов:
- Оповещение в Telegram.
- Автоматическое создание тикета в Jira.
- При повторном срабатывании подключаем дежурного инженера.
- Систематическое превышение — оценка и запуск масштабирования.
