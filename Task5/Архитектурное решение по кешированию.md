# Архитектурное решение по логированию
## Мотивация
**Текущие проблемы:**
- Медленная загрузка страницы со списком заказов в MES.
- Долгое выполнение операций обновления статусов.
- Повышенная нагрузка на базу данных при частом чтении списка заказов.
- Снижение производительности при росте количества клиентов.
- Увеличение времени ответа API в часы пиковой нагрузки.

**Бизнес-ценность кеширования:**
- Ускорение работы интерфейса операторов MES.
- Сокращение времени ожидания клиента при оформлении заказа.
- Снижение нагрузки на БД и увеличение ее стабильности.
- Повышение масштабируемости системы.
- Улучшение пользовательского опыта.

**Элементы системы для кеширования:**
- Список заказов (orders list).
- Детальная информация по заказу.
- Справочники (статусы, типы заказов).
- Часто запрашиваемые данные (количество заказов, статистика).
 
## Предлагаемое решение
**Вид кеширования**

Серверное кеширование с использованием Redis было выбрано по следующим причинам:
- Централизованный контроль данных.
- Возможность инвалидации.
- Подходит для микросервисной архитектуры.
- Не зависит от поведения клиента.

Клиентское кеширование не подходит по следующим причинам:
- Данные часто меняются.
- Необходимо контролировать консистентность.
- MES требует актуальных данных.

**Паттерн кеширования**

Паттерн Cache-Aside был выбран по следующим причинам:
- Самая простая реализация и широкая распространенность.
- Устойчивость к сбоям кеша.
- Модель данных в кеше может отличаться от модели данных в БД.

Другие паттерны не подходят по следующим причинам:
- Write-Through усложняет архитектуру и добавляет задержку при записи.
- Refresh-Ahead может привести к неконсистентности данных и чтению из базы, если система мониторинга некачественно реализована.

**Стратегии инвалидации кеша**

|| Временная инвалидация |Инвалидация, основанная на запросах | Инвалидация на основе изменений | Программная инвалидация | Инвалидация по ключу |
| --- | --- | --- | --- | --- | --- |
| Описание | Устанавливается фиксированное время жизни данных в кеше | Кеш инвалидируется каждый раз, когда приходит запрос на обновление данных | Кеш инвалидируется каждый раз, когда происходят изменения в данных | Предоставляет возможность явно указывать, когда кеш должен быть инвалидирован на основе определенных условий или событий в приложении | Позволяет инвалидировать кеш для конкретных данных или ключей |
| Позволяет сделать | Просто и быстро реализовать кеширования без привязки к логике приложения | Обеспечить актуальность данных сразу после действий пользователя | Гарантировать актуальность данных при любых изменениях, инициированных как пользователями, так и системой | Гибко управлять инвалидацией в соответствии со сложной бизнес-логикой | Точечно обновлять только изменившиеся данные, минимизируя объем инвалидации |
| Не позволяет сделать | Гарантировать актуальность данных при изменениях, произошедших до истечения TTL. Пользователи могут видеть устаревшую информацию | Обрабатывать изменения, которые происходят не по прямому запросу пользователя | Различать, какие именно данные изменились, если не привязана к конкретным ключам – может потребовать инвалидации больших объемов кеша | Реализовать без требования детального знания всех возможных сценариев и событий, что повышает риск ошибок | Автоматически определять зависимости между данными — нужно явно указывать, какие ключи инвалидировать при том или ином изменении |

Наиболее подходящей стратегией является инвалидация на основе изменений, так как она обеспечивает актуальность данных сразу после их изменения. Также можно использовать ее вместе с инвалидацией по ключу, чтобы очищать только измененные записи и минимизировать нагрузку на систему.
